### План: VLM на vLLM (пункт 4)

Зачем: разделение функционала (15 баллов за архитектуру). Модель — независимый контейнер
со своими зависимостями и OpenAI-совместимым API; API становится лёгким (SigLIP + Qdrant +
решение); VLM перезапускается, заменяется и масштабируется отдельно; на пилоте портала батчинг
vLLM даёт пропускную способность при многих пользователях. Скорость — побочно: оценка на глаз
VLM ~0,95 → ~0,5–0,6 с, запрос ~1,6 → ~1,2 с (не замер). В ТЗ vLLM не упоминается — плюс именно
как архитектура, а не как требование.

1. В API — `WINE_VLM_BACKEND=local|vllm`. `vllm`: оба прохода — HTTP к `vllm:8000`,
   `max_tokens=1` + logprobs; картинки отдавать уже уменьшенными нашим `_fit`, чтобы
   препроцессинг совпадал. `verdict.py` не меняется.
2. В compose — сервис `vllm` (`vllm/vllm-openai`, версия с поддержкой Qwen3-VL — сверить
   перед скачиванием), веса из `models/` на чтение, `--max-model-len` ~8k,
   `--gpu-memory-utilization` ~0,45 (доля от всех 24 ГБ, а не от нашего лимита 14 ГБ).
   Образ ~10 ГБ тянет владелец (Docker Hub нестабилен).
3. Прогон 100 фото → сравнить с `service-final`: top-1, «нет в каталоге», p95, VRAM.
4. Совпало → `vllm` по умолчанию, `local` — запасной.

**Что перепроверять.** VLM не генерирует, а берёт softmax следующего токена по нашим меткам;
из этого три числа с порогами в `verdict.py`: `vlm_prob` (выбор среди топ-5, < 0,8 → «уточните»),
`vlm_none_prob` (P(«0»), > 0,5 → «нет в каталоге»), `verify_prob` (попарная проверка P(«Да»),
< 0,3 → «нет в каталоге», то есть `{"slug": null}`). У vLLM они сдвинутся: другие ядра внимания
(bf16), свой препроцессор картинок, только top-k logprobs по словарю. Большинство значений
с большим запасом (по `service-final`: `verify_prob` < 0,01 или > 0,99 у 58 из 100; `vlm_prob` > 0,99 у 78),
у порогов — около дюжины фото (`verify_prob` 0,15–0,5 — 4, `vlm_prob` 0,65–0,9 — 7,
`vlm_none_prob` 0,35–0,65 — 2). Пороги не пересчитывать заранее — перепроверить прогоном;
подбирать заново, только если цифры разошлись.

## Задача одним предложением

По фото бутылки (сделанному пользователем в реальных условиях — на полке магазина, с телефона) нужно вернуть `slug` — идентификатор конкретного вина в каталоге организатора. Это **retrieval-задача** (поиск ближайшего соседа по эмбеддингу), а не классификация с фиксированным числом классов: новые вина добавляются ~50/день, и переобучать модель под каждое из них не нужно — достаточно добавить новый эмбеддинг в индекс.

## MVP-архитектура

```
Фото пользователя → SigLIP 2 → вектор → Qdrant топ-10
    → Qwen3-VL выбирает вино среди первых 5 (карточки 1–5 + эталонные фото; «0» — ни одна);
      места 6–10 остаются в порядке векторного поиска
    → Qwen3-VL проверяет топ-1 попарно: «одно и то же вино?» (этикетка, текст, форма бутылки, цвет)
    → verdict: match / not_found («нет в каталоге — вот аналоги»)
    → /v1/eval/predict: топ-1 slug или null («нет в каталоге»)   |   /v1/scan, /v1/search: решение + топ-10
```

Три компонента:
1. **SigLIP 2** (`google/siglip2-so400m-patch16-512`, только vision-башня) — превращает фото в вектор. Не обучается заново на каждое новое вино. Выбрана по рекомендации ТЗ; смена модели = одна переменная окружения + 3,5 минуты на переиндексацию.
2. **Qdrant** — векторная БД, хранит эмбеддинги всех вин каталога + их `slug`. Добавление нового вина = `upsert` одного вектора, без переобучения.
3. **VLM** (`Qwen3-VL-4B-Instruct`, включён по умолчанию; `WINE_VLM_ENABLED=0` — только картинка) — два прямых прохода без генерации: (а) выбор среди топ-5 → вероятности «1»…«5» / «0»; (б) попарная проверка топ-1 → вероятность «Да». Различает цвет, сладость, стилизованные названия; проверка отличает «другое вино того же производителя». top-1 **96,2%**, «нет в каталоге» у **30 из 33** вин вне каталога, верный ответ скрыт у 5 из 62. p95 **1,59 с**, max 1,61 с, ~10,3 ГБ VRAM. Детали → `docs/baseline-results.md`, «Итоговый пайплайн».

OCR (EasyOCR) был и удалён 28.09: с VLM он не добавлял точности, а стоил 0,35 с и 2 ГБ VRAM.

## Контракт с организатором (важно, не путать с нашим внутренним API)

- Эндпоинт: `POST /v1/eval/predict`
- Вход: `multipart/form-data`, поле `image`
- Выход: JSON `{"slug": "..."}`
- **Целевой SLA — 3 секунды** (из ТЗ). 10 секунд в `participant_test.sh` — это лишь порог, на котором скрипт сдаётся, а не цель. Факт: p95 = 416 мс (только картинка); итоговый пайплайн (VLM топ-5 + проверка) — **p95 1585 мс, max 1613 мс**.
- **Если вина нет в каталоге, `/v1/eval/predict` отдаёт `{"slug": null}`** (решение владельца, 28.09; скрипт организатора пишет его как `predicted_slug: null`). То же — `top1: null` в `/v1/search` и `/v1/scan`, по нему интерфейс показывает «Данное вино отсутствует в каталоге» + аналоги. «Уточните» (`ambiguous`) топ-1 не обнуляет. Вернуть ближайшее вино — `WINE_PREDICT_EMPTY_IF_ABSENT=0`.
- Организатор тестирует по одному фото за раз, без параллелизма
- Ground truth для eval-фото нам не выдаётся — точность считает только сам организатор
- Проверка идёт на двух наборах: публичном (у нас) и приватном (у кейсодержателя, прогон вживую на онлайн-звонке, на нашей машине)
- **Распознавание — лишь 50 баллов из 100.** Ещё 20 — функция после поиска («цифровой сомелье» или аналоги), 15 — архитектура и воспроизводимость, 10 — мобильный интерфейс карточки в стилистике портала, 5 — скорость
- Подробности и разбор `participant_test.sh` → см. `data/10. РСХБ.Цифра.pdf` и `docs/baseline-results.md`

## Ключевые факты, которые НЕЛЬЗЯ забывать (набитые шишки)

- **`Slug` ≠ ключ для сопоставления с файлом фото.** Slug мог измениться после загрузки фото (переименование вина), из-за чего расходится с именем файла на диске. Правильный ключ — колонка `Название фото` из CSV. Подробности → `docs/history/catalog-matching.md`.
- **~25% имён `Название фото`** — это оригинальные имена аплоада (кириллица, скриншоты, хэши), не slug-подобные строки. Сопоставление по имени для них принципиально невозможно — это не баг матчинга, а свойство данных.
- **В среднем 1 фото на 1 вино** в исходном датасете (лишь ~13 вин имеют >1 фото) — честный train/val split "выкинуть картинку из индекса" в большинстве случаев убивает единственный шанс модели найти это вино. Для валидации нужны либо аугментации, либо независимые query-фото.
- **Domain gap**: каталожные фото (студийные/чистые) ≠ фото пользователей (полка магазина, блики, окружение, угол). Валидация "каталог → каталог" даёт завышенную, обманчивую точность.
- **CSV в среднем на 79% сматчен** с оригинальным rar-архивом по имени файла (1652 из 2090). Остаток — либо доразбирается вручную (мелкие категории), либо закрывается парсингом сайта vino-svoe.ru напрямую (см. `docs/scraper.md`).
- Сайт `vino-svoe.ru` — официальная платформа РСХБ + ВинЛаб; `robots.txt` разрешает обход `/wines/*`. Использовать вежливый троттлинг (задержка между запросами), не параллелить агрессивно.
- **25 групп каталожных фото байт-идентичны** (50 вин): одна и та же картинка на разные slug. Различить их по изображению невозможно в принципе — никакая модель, кроп или OCR не помогут. Жёсткий потолок ~2,4%.
- **71 slug из CSV отсутствует на сайте** (страницы отдают 404, вина сняты с публикации), 65 slug есть только на сайте. Пересечение — 2032. Если закрытая таблица ответов построена по CSV-дампу, эти 71 недостижимы: фото для них взять неоткуда.
- **3 eval-фото из `eval.zip` — байт-в-байт подмножество `Реальные фото.zip`** (сверено по md5). Среди них есть заведомо трудное.
- **Расширение файла в eval врёт**: `019c68d0.jpg` физически является WebP. Формат определять по содержимому, а не по имени.
- **Свежий torchvision поднимает torch 2.8 → 2.14 (CUDA 13)** (так было с `pip install easyocr`). torchvision нужен процессору Qwen3-VL, пин `torchvision==0.23.0` стоит в `services/search-api/requirements.txt`. Если стек всё же сломался: вернуть `torch==2.8.0 torchvision==0.23.0` и переустановить `nvidia-*-cu12` с `--force-reinstall --no-deps` (удаление пакетов cu13 стирает общие с cu12 `.so`).
- **Docker Hub из сети разработки нестабилен**: 22.09 отдавал 503, 28.09 `python:3.12-slim` скачался, а `qdrant/qdrant` рвался на CDN (`connection reset`). Образы владелец тянет и собирает сам — Claude только пишет Docker-файлы и проверяет их статически (`docker compose config`, `bash -n`). Запасной путь без Docker — нативный Qdrant `infra/run-qdrant.sh` (та же версия и то же хранилище `data/qdrant/storage`).
- **В образах код лежит по путям репозитория (`/app/libs/...`, `/app/services/...`)**: настройки вычисляют корень проекта как `parents[4]` от модуля. Короткий путь (`/app/src/...`, как было в старом Dockerfile парсера) роняет импорт.
- **Прокси вида `http://127.0.0.1:PORT` из контейнера не виден** — поэтому `scraper` в compose в сети хоста (`network_mode: host`). API и индексатору интернет не нужен, прокси им не пробрасывается (иначе запросы к `qdrant:6333` ушли бы в прокси).
- **Без прогрева первый запрос к сервису — 3,4 с** (холодные CUDA-ядра и Qdrant) при SLA 3 с. В `lifespan` стоит холостой поиск по белой картинке — не убирать.
- **С VLM `score` больше не монотонен в выдаче**: порядок первых пяти задаёт `vlm_prob`, `confidence` = `vlm_prob`. Вероятность выбора VLM не откалибрована (0,9–1,0 и на ошибках) — «нет в каталоге» решает попарная проверка (`verify_prob`), а не она.
- **Больше кандидатов VLM — не лучше**: из топ-10 top-1 92,5% против 94–96% из топ-5 и +0,4 с — лишние кандидаты путают вина одной линейки (верное вино и так всегда в топ-5).
- **Проверка по этикетке и проверка по этикетке + форме бутылки + цвету вина + тексту дают одинаковые цифры** (31 из 33, 5 ложных); взята вторая — увереннее и не зависит от порога.
- **VLM, выбирая из многих, почти никогда не отвечает «0»** — называет самое похожее вино, даже когда на фото другое вино того же производителя. Отказ держится на попарной проверке «одна и та же этикетка?».
- **Эталонные PNG каталога тяжёлые (1–2,5 МБ, ~0,25 с на декодирование).** Десяток на запрос выталкивал ответ за SLA — VLM читает их из кэша уменьшенных копий `data/catalog/vlm-refs-<пиксели>/` (строится в фоне при старте сервиса).
- **Карточка на сайте иногда расходится с бутылкой на полке** (наш каталог совпадает с сайтом, разметка верна — исправлять у нас нечего): у Uva Vallis «Рислинг» (`uva-vallis-risling`) категория «Красное сухое», хотя сорт и цвет «Золотисто-соломенный» — белого вина (вероятно, опечатка на сайте; так же в CSV-дампе); у Golubitskoe «Red Blend» на сайте прежний дизайн этикетки, на полке — новый «Winery Series». VLM-проверка на таких отвечает «нет» — 2 из 5 скрытых верных ответов.
- **Весь исходящий трафик идёт через локальный Privoxy.** Два следствия: (1) localhost надо исключать из проксирования, иначе клиент Qdrant получает `503 Forwarding failure` — делается в рантайме через `bypass_proxy_for_localhost()`; (2) загрузчик HuggingFace на разрывах начинает файл заново и не докачивает — веса тянуть только через `infra/fetch-model.sh` (curl с резюмированием).
