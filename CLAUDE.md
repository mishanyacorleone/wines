# CLAUDE.md

Навигатор по проекту распознавания вин по фото этикетки (хакатон). Читай этот файл первым — он объясняет, что за задача, где что лежит, и куда идти за деталями.

## Задача одним предложением

По фото бутылки (сделанному пользователем в реальных условиях — на полке магазина, с телефона) нужно вернуть `slug` — идентификатор конкретного вина в каталоге организатора. Это **retrieval-задача** (поиск ближайшего соседа по эмбеддингу), а не классификация с фиксированным числом классов: новые вина добавляются ~50/день, и переобучать модель под каждое из них не нужно — достаточно добавить новый эмбеддинг в индекс.

## MVP-архитектура

```
Фото пользователя → SigLIP 2 → вектор → Qdrant топ-20 ┐
                 → EasyOCR → слова этикетки ──────────┴→ переранжирование → топ-5
                                                            → [Qwen3-VL выбирает внутри топ-5] → slug + confidence
```

Четыре компонента (VLM — опциональный, за флагом):
1. **SigLIP 2** (`google/siglip2-so400m-patch16-512`, только vision-башня) — превращает фото в вектор. Не обучается заново на каждое новое вино. Выбрана по рекомендации ТЗ; смена модели = одна переменная окружения + 3,5 минуты на переиндексацию.
2. **Qdrant** — векторная БД, хранит эмбеддинги всех вин каталога + их `slug`. Добавление нового вина = `upsert` одного вектора, без переобучения.
3. **OCR** (EasyOCR ru+en, включён по умолчанию) — вина одной линейки с почти одинаковой этикеткой (разный сорт, другой оттенок) сливаются в эмбеддинге; текст этикетки их разводит. 77,4% → 88,7% top-1.
4. **VLM-реранкер** (`Qwen3-VL-4B-Instruct`, **выключен по умолчанию**, `WINE_VLM_ENABLED=1` в `.env`) — получает фото и пять кандидатов (текст карточки + эталонное фото) и за один прямой проход без генерации отдаёт вероятности «1»…«5» / «0» (ни одна не подходит). Различает цвет, сладость, стилизованные названия. 88,7% → **96,2%** top-1; с ним OCR не нужен (та же точность), рекомендуемая связка — VLM вкл., OCR выкл. Цена: +9 ГБ VRAM, p95 1,68 с. Детали → `docs/baseline-results.md`, раздел «VLM-реранкер топ-5».

## Контракт с организатором (важно, не путать с нашим внутренним API)

- Эндпоинт: `POST /v1/eval/predict`
- Вход: `multipart/form-data`, поле `image`
- Выход: JSON `{"slug": "..."}`
- **Целевой SLA — 3 секунды** (из ТЗ). 10 секунд в `participant_test.sh` — это лишь порог, на котором скрипт сдаётся, а не цель. Факт: p95 = 416 мс (только картинка), 835 мс (с OCR, по умолчанию), 1682 мс (VLM без OCR, max 2,3 с).
- Организатор тестирует по одному фото за раз, без параллелизма
- Ground truth для eval-фото нам не выдаётся — точность считает только сам организатор
- Проверка идёт на двух наборах: публичном (у нас) и приватном (у кейсодержателя, прогон вживую на онлайн-звонке, на нашей машине)
- **Распознавание — лишь 50 баллов из 100.** Ещё 20 — функция после поиска («цифровой сомелье» или аналоги), 15 — архитектура и воспроизводимость, 10 — мобильный интерфейс карточки в стилистике портала, 5 — скорость
- Подробности и разбор `participant_test.sh` → см. `data/10. РСХБ.Цифра.pdf` и `docs/baseline-results.md`

## Ключевые факты, которые НЕЛЬЗЯ забывать (набитые шишки)

- **`Slug` ≠ ключ для сопоставления с файлом фото.** Slug мог измениться после загрузки фото (переименование вина), из-за чего расходится с именем файла на диске. Правильный ключ — колонка `Название фото` из CSV. Подробности → `docs/catalog-matching.md`.
- **~25% имён `Название фото`** — это оригинальные имена аплоада (кириллица, скриншоты, хэши), не slug-подобные строки. Сопоставление по имени для них принципиально невозможно — это не баг матчинга, а свойство данных.
- **В среднем 1 фото на 1 вино** в исходном датасете (лишь ~13 вин имеют >1 фото) — честный train/val split "выкинуть картинку из индекса" в большинстве случаев убивает единственный шанс модели найти это вино. Для валидации нужны либо аугментации, либо независимые query-фото.
- **Domain gap**: каталожные фото (студийные/чистые) ≠ фото пользователей (полка магазина, блики, окружение, угол). Валидация "каталог → каталог" даёт завышенную, обманчивую точность.
- **CSV в среднем на 79% сматчен** с оригинальным rar-архивом по имени файла (1652 из 2090). Остаток — либо доразбирается вручную (мелкие категории), либо закрывается парсингом сайта vino-svoe.ru напрямую (см. `docs/scraper.md`).
- Сайт `vino-svoe.ru` — официальная платформа РСХБ + ВинЛаб; `robots.txt` разрешает обход `/wines/*`. Использовать вежливый троттлинг (задержка между запросами), не параллелить агрессивно.
- **25 групп каталожных фото байт-идентичны** (50 вин): одна и та же картинка на разные slug. Различить их по изображению невозможно в принципе — никакая модель, кроп или OCR не помогут. Жёсткий потолок ~2,4%.
- **71 slug из CSV отсутствует на сайте** (страницы отдают 404, вина сняты с публикации), 65 slug есть только на сайте. Пересечение — 2032. Если закрытая таблица ответов построена по CSV-дампу, эти 71 недостижимы: фото для них взять неоткуда.
- **3 eval-фото из `eval.zip` — байт-в-байт подмножество `Реальные фото.zip`** (сверено по md5). Среди них есть заведомо трудное.
- **Расширение файла в eval врёт**: `019c68d0.jpg` физически является WebP. Формат определять по содержимому, а не по имени.
- **`pip install easyocr` без пина torchvision поднимает torch 2.8 → 2.14 (CUDA 13).** Пин стоит в `services/search-api/requirements.txt`. Если стек всё же сломался: вернуть `torch==2.8.0 torchvision==0.23.0` и переустановить `nvidia-*-cu12` с `--force-reinstall --no-deps` (удаление пакетов cu13 стирает общие с cu12 `.so`).
- **Docker Hub недоступен из сети разработки** (503, зеркало gcr тоже). Qdrant поднимается нативным бинарником `infra/run-qdrant.sh`.
- **Без прогрева первый запрос к сервису — 3,4 с** (холодные CUDA-ядра и Qdrant) при SLA 3 с. В `lifespan` стоит холостой поиск по белой картинке — не убирать.
- **С VLM `score` больше не монотонен в выдаче**: порядок пятёрки задаёт `vlm_prob`, `confidence` = `vlm_prob`. Вероятность VLM не откалибрована (0,9–1,0 и на ошибках) — не использовать её как порог уверенности без проверки.
- **Весь исходящий трафик идёт через локальный Privoxy.** Два следствия: (1) localhost надо исключать из проксирования, иначе клиент Qdrant получает `503 Forwarding failure` — делается в рантайме через `bypass_proxy_for_localhost()`; (2) загрузчик HuggingFace на разрывах начинает файл заново и не докачивает — веса тянуть только через `infra/fetch-model.sh` (curl с резюмированием).

## Открытые вопросы

- **Что вернуть, если вина нет в каталоге.** В публичной выборке таких фото треть (33 из 100). Как организатор это оценивает и какой ответ ждёт — неизвестно. Сигналы есть: порог по баллу картинки (70/84) и ответ VLM «0» (6 из 33 без ложных), но отказ не реализован.
- **С чем идти на проверку**: по умолчанию (OCR, 88,7%, 0,8 с, 3 ГБ) или VLM (96,2%, 1,7 с, 10 ГБ). Проверка приватного набора идёт на нашей машине — VRAM и время надо сверить на ней в день проверки.
- **Регламент о парсинге.** В ТЗ прямого запрета на сторонние источники нет, но и явного разрешения тоже: каталог формально «передаётся дампом базы». Мы строим индекс по сайту кейсодержателя — риск низкий, но это решение, а не факт.
- **71 slug только в CSV.** Если ответы кейсодержателя построены по дампу, эти вина недостижимы. Закрыть можно только оригинальным rar-архивом с фото — на диске его нет.
- **Имена в `Реальные фото.zip`** (вида `96.31_09-09-2026_19-29-01.webp`) выглядят как «score_дата_время», но подтверждения этому нет. Ориентироваться на них при оценке нельзя.

## Стек

- Python 3.12, Pillow, pandas — разбор данных
- SigLIP 2 (`google/siglip2-so400m-patch16-512`) через `transformers` + torch 2.8 (CUDA) — энкодер изображений
- Qdrant 1.19.1 — векторный индекс (косинус, dim 1152)
- httpx + BeautifulSoup — парсер сайта
- EasyOCR 1.7.2 (`ru`+`en`, веса в `models/easyocr`) + rapidfuzz — чтение этикетки и нечёткое сравнение
- Qwen3-VL-4B-Instruct (bf16, `models/Qwen3-VL-4B-Instruct`) через `transformers` 4.57.1 — VLM-реранкер
- python-dotenv — чтение `.env`
- FastAPI + uvicorn — сервис поиска

Железо: RTX 3090, из них нам отведено **не более 14 ГБ VRAM** — на машине работают
посторонние сервисы. Лимит выставляется жёстко в коде; фактический пик — 1,67 ГБ при индексации,
~3,2 ГБ у API с OCR, ~10 ГБ у API с VLM без OCR (VLM + OCR — ~12 ГБ).
