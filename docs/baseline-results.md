«ощутимом отрыве», позволяющем убрать экран вариантов, сейчас не выполняется.**

## Точность

Не измерена автоматически: ground truth кейсодержатель не выдаёт. Размечается
вручную по HTML-отчёту (`data/reports/report.html`), отметки хранятся в
localStorage и выгружаются в JSON для сравнения прогонов.

## Качественное наблюдение

По превью выдача выглядит правдоподобно, но при внимательном сравнении
различается не то: вина одной линейки с почти одинаковой этикеткой путаются,
хотя у них разный сорт винограда или другой цвет этикетки (красная против
оранжевой).

Причина арифметическая: в кадре 3024×4032 бутылка занимает 10–15%, после паддинга
до квадрата и сжатия до 512 на этикетку остаётся 60–80 пикселей по ширине. Мелкий
текст на такой картинке не разрешается, цвета размываются. Модель сравнивает
силуэт, компоновку и доминирующий цвет — ровно то, что у вин одной линейки
совпадает.

## Направления улучшения

По убыванию отношения «эффект / трудозатраты»:

1. **Кроп бутылки перед энкодером.** Детектор бутылки → эффективное разрешение этикетки растёт в 5–10 раз,
   плюс исчезает domain gap. Прямая подсказка кейсодержателя про нормализацию.
2. **Геометрическая верификация** топ-10 по локальным признакам
   (SuperPoint+LightGlue или ORB): проверка «та же самая этикетка», а не «похожая».
3. **OCR + переранжирование** по `title`/`manufacturer`/`grapes` из payload —
   разводит вина одной линейки с разным сортом. Запас по SLA позволяет.
4. **Цветовой дескриптор** области этикетки для тайбрейка — бьёт в случай
   «красная против оранжевой», где CLIP-подобные модели традиционно слабы.
5. **Дообучение (ArcFace/triplet)** на аугментированном каталоге с hard negatives
   из вин одной линейки — самый высокий потолок и самые большие трудозатраты.

Слияние нескольких сигналов даст и осмысленный `margin`, которого сейчас нет.

## Жёсткий потолок

25 групп каталожных фотографий байт-идентичны (50 вин, см. `history/catalog-matching.md`).
Различить их по изображению невозможно в принципе — ни один из пунктов выше не
поможет. Это ~2,4% каталога, где нужен либо сигнал из метаданных, либо явный
отказ от выбора.

## Кандидаты на сравнение

Смена модели — одна переменная окружения плюс переиндексация (3,5 минуты):

| Модель | Чем интересна |
|---|---|
| `google/siglip2-so400m-patch16-512` | текущая; рекомендация ТЗ, разрешение 512 |
| `facebook/dinov3-vitl16`, `dinov2-large` | self-supervised, сильны на instance retrieval |
| `openai/clip-vit-large-patch14-336` | классический бейзлайн для сравнения |
| `google/siglip2-base-patch16-512` | вчетверо легче, если понадобится скорость |

Сравнивать на той же сотне фото с уже сделанной разметкой — повторно размечать
не придётся.

# OCR-переранжирование

Второй замер. Дата: 23.09.2026.

## Зачем

До OCR в 76 из 100 запросов топ-1 и топ-2 были от одного производителя, в 51 —
все пять кандидатов. Картинка надёжно находит линейку, но внутри неё выбирает
почти случайно. Текст этикетки при этом крупный и читаемый: сорт, цвет, сладость.

## Как устроено

1. Картинка → топ-20 кандидатов из Qdrant (как раньше, только глубже).
2. EasyOCR (`ru`+`en`, фото уменьшено до 1280 по длинной стороне) → строки текста.
3. Для каждого кандидата: какие слова его карточки (`title`, `manufacturer`,
   `category`, `grapes`) нашлись на этикетке. Вес слова — IDF по каталогу.
   `text_score = min(Σ IDF / 40, 1) − 0.15 × (число групп цвет/сладость,
   где этикетка противоречит карточке)`.
4. `score = cos + 0.15 · text_score`, сортировка, softmax → confidence.

Шум OCR, с которым пришлось бороться (всё — на реальных фото):

| Проблема | Пример | Решение |
|---|---|---|
| «Л»/«Д» читаются как «А» | «МУСКАТЕАЬ», «МАССАНАРА» | нечёткое сравнение, `fuzz.ratio ≥ 80` в транслите |
| Слово рвётся пробелом | «СИР А», «Т А Б И Я» | склейка соседних слов строки |
| Кириллица вперемешку с латиницей | «KАБЕ₽HЕ» | похожие латинские буквы → кириллица |
| Бренд в двух алфавитах считался дважды | «Fanagoria» + «Фанагория» | одно слово в двух написаниях — одна улика |
| Латинские «EXTRA BRUT» — редкие слова | вытаскивали чужой брют | brut/extra/rose → брют/экстра/розовое |
| Обрывок с края кадра | «бел:» ≈ «белое» | точная основа — только для слов длиннее 3 букв |
| Текст соседней бутылки | «МУСКАТ КРАСНОГО» рядом с белым | цвет, названный в самом `title`, штраф отменяет |

Первая версия считала *долю* найденных слов — это награждало кандидатов
с коротким описанием, и выбор уходил к вину, у которого просто меньше слов.
Заменено на абсолютную сумму: общие для линейки слова дают всем одинаковую
прибавку, порядок решают различающие.

## Честная оговорка

Вес (0,15), потолок (40) и штраф (0,15) подобраны сеткой на **10 фото,
проверенных вручную** — это подгонка, а не измерение точности. Реальную
цифру даст только разметка всех 100 фото: сравнить top-1/top-5 с
`WINE_OCR_ENABLED=0` и `=1` (отчёт с OCR — `data/reports/ocr/report.html`,
там видны прочитанный текст и разбивка балла на каждого кандидата).

## Что OCR не решает

- Рукописные и каллиграфические шрифты не читаются («Совиньон Блан» у Литавщука).
- Латинское название сорта не сопоставляется с русским («CABERNET» ≠ «каберне»,
  «SYRAH» ≠ «сира») — нужен словарь синонимов сортов.
- Если вина нет в каталоге, OCR не отказывает, а выбирает ближайшее по словам.

# VLM-реранкер топ-5

Даты: 26.09.2026 — офлайн-эксперимент, 27.09.2026 — встроен в сервис и перепроверен.
Все прогоны и формулы — `data/reports/accuracy.xlsx` (лист «Итог» + лист на
каждый прогон), пересборка — `python -m eval_runner.excel`.

## Зачем

Верное вино всегда в топ-5, ошибки — выбор внутри линейки. Для него нужны
признаки, которых нет у эмбеддинга и OCR: **цвет вина в бутылке**, сладость,
стилизованные и мелкие названия. VLM видит этикетку целиком и может сверить её
с карточками кандидатов.

## Как устроено

- Модель: **Qwen3-VL-4B-Instruct**, bf16, `models/Qwen3-VL-4B-Instruct` (8,9 ГБ,
  скачивается `infra/fetch-vlm.sh`). Лимит VRAM процесса общий с энкодером.
- Вход: фото пользователя + пять карточек кандидатов, по порядку текущей выдачи.
  Карточка — `название — производитель — категория; сорта: …` и (в лучшем
  варианте) эталонное фото из каталога. Промпт просит сверить название,
  производителя, сорт, цвет и сладость и ответить одной цифрой; «0» — ни одна
  карточка не подходит.
- **Генерации нет.** Один прямой проход, из логитов следующего токена берутся
  только токены «0»…«5», по ним softmax. Получается распределение вероятностей,
  а не строка; время не зависит от разговорчивости модели.
- Пятёрка пересортировывается по вероятности VLM, остальные кандидаты идут следом
  в прежнем порядке. `confidence` = вероятность VLM, `vlm_none_prob` = вероятность «0».
- Картинки уменьшаются по площади до лимита: число визуальных токенов Qwen3-VL
  растёт с площадью (токен на 32×32 px), а с ним время.

| только картинка | нет | — | — | 77,4% | 77,3% | — | 416 |

VLM-вариантов = 100% (VLM только переставляет пятёрку).

Выводы:

- **Эталонные фото кандидатов важнее текста**: 94,3% → 96,2%. Цвет вина и
  оформление этикетки VLM сверяет по картинке.
- **С VLM OCR перестаёт давать прирост** — та же точность без него, и минус
  ~350 мс OCR и ~2 ГБ VRAM. Поэтому лучший вариант — VLM без OCR.
- Уменьшение картинок почти бесплатно по точности и срезает p95 VLM с 1,7 до 1,2 с.
- Сервис воспроизвёл офлайн-результат один в один (та же выдача на всех 100 фото).
- Пик VRAM процесса API с VLM без OCR — ~10 ГБ из 14.

## Что VLM исправил и где ошибается (лучший вариант против OCR)

Исправлено 5 уверенных и 2 «не уверен»:

- **Линейка Denisov — все 3** (Пет-Нат Рубин, Пазори Рислинг, Барыня. Курмыши):
  стилизованные названия, которые OCR не читал.
- **Литавщук «Поздний сбор, Красное»** и **Golubitskoe Red Blend** — цвет,
  видимый глазом.
- **Формула Q** (регрессия OCR) и **AYA Purity** — из «не уверен».

Ошибки:

- **Регрессия — 1:** Усадьба Перовских «Полусухое красное» → VLM уверенно
  (P = 1,00) выбрал «Полусладкое красное» той же линейки.
- **АРАТТИ «Каберне по-белому»** — в каталоге две карточки с одним названием:
  «Красное сухое» и «Розовое полусухое». Разметка — красное, VLM выбрал розовое;
  на фото вино светлое, разметка спорная.
- 2 фото «не уверен», где точного вина в каталоге нет (Фанагория Rose, LETO
  Шардоне) — выбран ближайший.

Вероятность VLM почти всегда 0,9–1,0, и на ошибках тоже — как мера уверенности
она пока не откалибрована.

## Отказ «нет в каталоге» по ответу «0»

При пороге `vlm_none_prob > 0,5` отказ ловит **6 из 33** фото вне каталога при
**0 из 66** ложных отказов. Сигнал чистый, но редкий: VLM предпочитает выбрать
похожее вино из той же линейки. Одного его мало — нужна комбинация с баллом
картинки (порог по баллу разделяет 70 из 84).

# Итоговый пайплайн: VLM по топ-10 + проверка «нет в каталоге»

Дата: 28.09.2026. Решение владельца: OCR убрать, VLM выбирает из **топ-10**
векторного поиска, наружу — отдельно топ-1 (метрика) и топ-10 (интерфейс).

## Что изменилось

- **Карточки помечены буквами A–J**, а не цифрами: «10» — два токена, буква —
  один. «0» по-прежнему значит «ни одна не подходит».
- **Второй проход — попарная проверка** выбранного топ-1 (`VlmReranker.verify`):
  фото пользователя + эталонное фото + описание карточки, вопрос «На обоих фото
  одна и та же этикетка?», вероятность «Да» против «Нет». ~150 мс.
- OCR (`ocr.py`, `text_match.py`, EasyOCR) из пайплайна удалён.
