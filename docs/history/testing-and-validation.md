# Тестирование и валидация без ground truth

Ключевая сложность проекта: у нас нет размеченных пар для честной проверки точности на реалистичных фото. Этот документ фиксирует, почему "очевидные" подходы к валидации не работают в нашем случае, и что делать вместо них.

## Почему обычный train/val split здесь не работает

Стандартный подход — отложить 15-20% каталога, построить индекс на остальном, проверить, находит ли модель отложенные фото. **В нашем случае это в основном не работает**, потому что:

- В каталоге **в среднем 1 фото на 1 вино** (см. `history/catalog-matching.md` — только ~13 вин имеют больше одного фото).
- Если выкинуть единственное фото вина из индекса — для него **физически невозможно** получить правильный ответ: индекс просто не содержит эту сущность. Модель неизбежно найдёт какое-то другое, ближайшее по виду вино — и это будет засчитано как "ошибка", хотя дело не в качестве модели, а в отсутствии multi-view данных.

Единственный честный кусок для классического train/val — те ~13 вин с несколькими фото (одно оставить в индексе, второе отложить и проверить, найдёт ли модель то же самое вино). Слишком маленькая выборка для статистически значимой оценки, но полезна как sanity-check.

## Второй подводный камень: domain gap

Наши каталожные фото — студийные/чистые (либо продуктовые фото с сайта). Реальные query-фото от пользователей — с телефона, на полке магазина, с окружением, бликами, под углом (см. пример в `eval.zip/queries/`).

**Валидация "каталог → каталог"** (даже там, где технически возможна) даёт завышенную, слишком оптимистичную оценку — она не отражает, как модель справится с реальными фото пользователей, потому что вообще не проверяет устойчивость к domain gap.

## Что делать вместо этого — два взаимодополняющих пути

### Путь 1: аугментации как дешёвая прокси-метрика

Взять каждую каталожную картинку, применить к копии случайные искажения, имитирующие условия реальной съёмки:
- Поворот/наклон
- Случайная обрезка (crop)
- Изменение яркости/контраста, добавление бликов
- Возможно — вставка на фоновое изображение (имитация "на полке")

Проверить, находит ли CLIP оригинал по искажённой копии. Не идеальная метрика (мы сами создаём "похожесть", а не берём независимые данные), но:
- Покрывает весь каталог сразу, без ручной работы.
- Дёшево пересчитывается при каждой итерации (смена модели, параметров).
- Полезна для быстрой относительной оценки ("стало лучше/хуже после изменения X"), а не для абсолютной точности.

### Путь 2: реальные query-фото — основное мерило

- 3 тестовых фото из `eval.zip/queries/` — уже есть, использовать для первой проверки.
- 100 доп. query-фото, присланных организатором позже (тоже без разметки) — прогнать pipeline и оценить глазами (или, если возможно, свериться со slug'ами вручную, сверяя визуально этикетку с найденным top-1/top-5 кандидатом).
- Дополнительно — можно самостоятельно сфотографировать несколько бутылок телефоном в условиях, близких к реальным (полка, разное освещение), если под рукой есть вина из каталога.

Это единственный способ получить оценку, реально отражающую условия эксплуатации.

## Практический подход к измерению на query-фото без разметки

Раз автоматической метрики точности нет, подход — полуручной:
1. Прогнать pipeline, получить top-5 кандидатов на каждое query-фото (не только top-1 — так проще заметить "почти правильные" случаи).
2. Для каждого query-фото положить его рядом с top-5 найденными каталожными фото (визуализация бок о бок).
3. Глазами оценить: совпадает ли этикетка визуально с одним из кандидатов, и на каком месте (1-5) правильный ответ оказался, если распознаётся.
4. Считать долю "top-1 верно" и "top-5 верно" (даже такая грубая, ручная оценка на 3-100 фото — уже значимо лучше, чем ничего).

Если совпадений в топ-5 нет вообще ни на одном фото — это сигнал, что нужно смотреть на domain gap серьёзно (аугментации при построении индекса, другая модель, или переход к metric learning вместо zero-shot).

## Официальный eval (для контекста)

Организатор проверяет через `participant_test.sh` (см. `CLAUDE.md`/`data-sources.md`) — точность считается только на его стороне, ground truth нам недоступен ни при каких условиях. Наша офлайн-валидация (пути 1 и 2 выше) — единственный способ понять качество решения до отправки на официальную проверку.
