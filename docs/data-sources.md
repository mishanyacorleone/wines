# Источники данных

Четыре исходных файла/архива от организатора + один внешний источник (сайт), который парсим сами.

Реальная структура на диске:
```
data/
├── 10. РСХБ.Цифра.pdf
└── Датасет (1)/
    ├── eval.zip
    ├── strapi_output0709.csv
    └── Реальные фото.zip
```

## 1. `eval.zip` — протокол оценки

Это не датасет, а **контракт**, как организатор будет проверять решение.

Содержимое:
- `README.md` — описание требований к сервису
- `queries.tsv` — манифест тестовых запросов (`query_id`, `image_path`)
- `queries/` — 3 тестовых фото для примера/дебага (реальные фото с телефона на полке магазина, 3024×4032, с соседними бутылками в кадре, бликами — НЕ студийные)
- `checksums.sha256` — контрольные суммы файлов
- `participant_test.sh` — bash-скрипт организатора, который будет дёргать сервис

Ключевые условия из `participant_test.sh`:
- Шлёт фото по одному (без параллелизма), `multipart/form-data`, поле `image`
- Endpoint по умолчанию: `http://127.0.0.1:8080/v1/eval/predict`
- Таймаут: 10 сек на запрос (`--max-time 10`), коннект 5 сек
- Ждёт JSON: `{"slug": "..."}` либо `[{"slug": "..."}]` (топ-1 из массива тоже сработает)
- Если что-то не так — `predicted_slug` будет `null`, скрипт не падает
- Результат сохраняется в `predictions.jsonl`: `query_id`, `image_path`, `image_sha256`, `predicted_slug`, `latency_ms`
- **Ground truth для eval-фото нам не выдаётся** — точность считает только организатор

Позже организатор прислал ещё 100 нетестовых query-фото (реальные условия съёмки) — тоже без разметки.

## 2. `strapi_output0709.csv` — каталог-справочник

Экспорт из Strapi CMS, 4147 строк (с дублями), **2103 уникальных `Slug`**.

Колонки: `Название вина`, `Категория`, `Цвет`, `Регион`, `Сорт винограда`, `Описание`, `Винодельня`, `Slug`, `Название фото`.

Важно:
- В сырых данных много **полных дублей строк** (артефакт экспорта Strapi) — обязательно `drop_duplicates()` перед использованием.
- `Slug` — URL-идентификатор вина на сайте `vino-svoe.ru/wines/<slug>`, то же самое значение, которое нужно возвращать в eval-ответе.
- `Название фото` — имя файла на момент загрузки в Strapi. **Это не то же самое, что имя файла в архиве** — см. `catalog-matching.md`.
- В среднем 1 фото на 1 вино (multi-view данных почти нет — только ~13 вин имеют больше одного фото, и то по случайности переиспользования).

## 3. `prod-svoe-vino-strapi.part1/2/3.rar` — архив с фото

Многотомный RAR, распаковывается в 15803 файлов по пути:
```
prod-svoe-vino-strapi/prod-svoe-vino/strapi/uploads/<filename>
```

Среди них:
- **9562 файла — авто-превью Strapi** (`thumbnail_*`, `small_*`, `medium_*`, `large_*`) — не основные файлы, при матчинге исключаются.
- **6241 файл-оригинал** — из них реально сматчено с каталогом 1652 (79%), см. `catalog-matching.md` за деталями и оставшимися 21%.

## 5. `Реальные фото.zip` — реальные фото от живых людей

**Не разобран в этом документе.** По описанию — фото, снятые реальными людьми на камеру (в отличие от `eval.zip/queries/`, где всего 3 примера от организатора). Неизвестно:
- Сколько фото внутри
- Есть ли разметка (manifest/csv со slug'ами) рядом, или это просто набор картинок без привязки к каталогу
- Формат, разрешение, условия съёмки

Если внутри есть разметка — это резко меняет план валидации (`testing-and-validation.md`): вместо ручной, глазами, оценки на паре десятков фото появляется возможность посчитать честный accuracy автоматически, на реалистичных (не студийных) фото. Разобрать этот архив — один из первых практических шагов, если задача — понять, насколько pipeline готов к реальному использованию.

## 6. Сайт vino-svoe.ru — используется как дополнительный источник

Официальная платформа РСХБ + ВинЛаб (продвижение российского виноделия), не мелкий частный проект. `robots.txt` разрешает обход `/wines/*` (запрещён только `/api/*`, относящийся к отдельному поддомену `api.vino-svoe.ru`).

- Полный список URL всех вин каталога: `https://vino-svoe.ru/wines-sitemap.xml` — **2067 URL**, из них 2033 совпадают по `slug` напрямую с CSV (97% пересечения — расхождение объясняется тем, что каталог живой и обновляется между экспортом CSV и текущим моментом).
- Каждая страница вина построена на Nuxt.js SSR и содержит блок `<script id="__NUXT_DATA__">` со структурированными данными (slug, title, image, region, manufacturer, category, description) — надёжнее, чем парсить вёрстку. Подробный разбор формата и рабочий код → `scraper.md`.
- Используется, чтобы закрыть пробелы там, где матчинг CSV↔архив не сработал (21% каталога), и как более надёжный/официальный источник самих фото и slug'ов в целом.
