# Архитектура

Сервис распознаёт вино по фотографии этикетки и возвращает карточку из каталога
«Своё Вино». Задача решается как **retrieval**, а не классификация: каталог
пополняется примерно на 50 позиций в день, и переобучать модель под каждое новое
вино нельзя. Новое вино = один новый вектор в индексе.

## Границы слоёв

```
                  ┌───────────────────────┐
 vino-svoe.ru ───▶│   catalog-scraper     │──▶ data/catalog/
                  │  sitemap → NUXT → PNG │     images/*.png + catalog.jsonl
                  └───────────────────────┘
                                                      │
                  ┌───────────────────────┐           │
                  │       indexer         │◀──────────┘
                  │ фото → вектор → upsert│
                  └───────────┬───────────┘
                              ▼
                        ┌──────────┐
                        │  Qdrant  │  2097 точек, dim 1152, cosine
                        └────┬─────┘
                             ▲
 фото с телефона   ┌─────────┴─────────────┐
      ────────────▶│      search-api       │──▶ JSON: топ-1 + топ-10 + «нет в каталоге»
                   │ нормализация → вектор │
                   │ → поиск → VLM → verify│
                   └───────────────────────┘
                             ▲
                   ┌─────────┴─────────────┐
                   │      eval-runner      │──▶ HTML-отчёт + замеры времени
                   └───────────────────────┘
```

| Компонент | Ответственность | Чего НЕ делает |
|---|---|---|
| `libs/wine-embeddings` | модель, нормализация фото, лимит VRAM, кэш весов | ничего не знает про Qdrant и HTTP |
| `services/catalog-scraper` | сбор каталога с сайта | не считает эмбеддинги |
| `services/indexer` | каталог → векторы → Qdrant | не обслуживает запросы |
| `services/search-api` | HTTP-контракт, поиск, VLM-выбор и проверка, решение «нет в каталоге» | не строит индекс |
| `tools/eval-runner` | прогон выборки, метрики времени, отчёт | не лезет в Qdrant напрямую, работает только через API |

## Ключевое архитектурное решение: общий энкодер

`libs/wine-embeddings` вынесен в отдельную библиотеку, которую используют и
индексатор, и API. Это не борьба с дублированием кода, а корректность: если
индекс построен одним препроцессингом, а запрос кодируется другим, векторы
окажутся в разных частях пространства. Поиск при этом продолжит «работать» —
просто станет возвращать мусор, и ни логи, ни тесты этого не покажут.

## Поток обработки запроса

1. **Нормализация** (`wine_embeddings.preprocessing`) — EXIF-поворот, альфа-канал
   на белый фон, паддинг до квадрата без растяжения. Каталожные PNG вертикальные
   (медиана 340×1080), фото с телефона — 3024×4032; прямой resize деформировал бы
   бутылку в этих случаях по-разному.
2. **Эмбеддинг** (`wine_embeddings.encoder`) — SigLIP 2, только vision-башня;
   текстовая не загружается, поиск идёт картинка-к-картинке. Вектор L2-нормализуется,
   поэтому скалярное произведение в Qdrant и есть косинус.
3. **Поиск** — Qdrant, косинусная метрика, топ-k с payload (slug, url, метаданные).
   Payload самодостаточен: после поиска второго похода в базу нет.
4. **Выбор VLM** (`search_api.vlm`, `WINE_VLM_ENABLED=0` — выключить) —
   Qwen3-VL-4B получает фото пользователя и первые 5 из топ-10 (текст карточки +
   уменьшенное эталонное фото, кэш `data/catalog/vlm-refs-*`) и за один прямой
   проход без генерации отдаёт вероятности ответов «A»…«E» и «0» (ни одна не
   подходит). Пятёрка пересортировывается по ним, места 6–10 идут следом в
   порядке векторного поиска — это рекомендации для интерфейса. Картинка надёжно находит
   линейку (top-5 = 100%), VLM выбирает внутри неё — различает цвет, сладость и
   стилизованные надписи.
5. **Проверка топ-1** (`VlmReranker.verify`) — второй проход, ~150 мс: фото +
   эталон выбранного вина, «одно и то же вино?» (этикетка, текст на бутылке,
   форма бутылки, цвет вина) → вероятность «Да». Выбирая
   из многих, VLM почти всегда называет самое похожее вино; попарный вопрос
   отличает «другое вино того же производителя» — на нём держится «нет в каталоге».
   OCR (EasyOCR) был здесь до 28.09.2026 и убран: с VLM он не добавлял точности.
6. **Ранжирование** (`search_api.search`) — без VLM softmax с температурой 0.05 переводит
   баллы в `confidence`, с VLM `confidence` — его вероятность. Без температуры распределение было бы почти равномерным:
   соседние кандидаты различаются в сотых долях. Отдельно считается `margin` —
   отрыв первого от второго, прямое требование ТЗ.

## Контракты API

| Метод | Назначение |
|---|---|
| `POST /v1/search` | `top1` (slug для метрики) + топ-k (по умолчанию 10): slug, ссылка, метаданные, confidence, разбивка времени + решение `status`/`reason`/`message`, `verify_prob` |
| `POST /v1/eval/predict` | контракт скрипта кейсодержателя: плоский `{"slug": "..."}` |
| `POST /v1/scan` | ручка мобильного сканера: решение + карточка с советами сомелье или «нет в каталоге — вот аналоги» + топ-10 |
| `GET /v1/wines/{slug}`, `GET /v1/pairing`, `GET /v1/pairing/dishes` | карточка по выбору пользователя, вина к блюду |
| `POST /v1/feedback` | отклик «да / выбрал другое / моего нет» → `data/feedback/feedback.jsonl` |
| `GET /app/` | мобильный интерфейс (статика из `search_api/web`) |
| `GET /health` | модель, устройство, число точек в индексе, включён ли VLM, есть ли в индексе данные для сомелье |

## После поиска: решение и сомелье

```
выдача топ-10 ──▶ verdict.decide ──▶ match ──▶ карточка топ-1 + sommelier.advise + sommelier.similar
                                   └─▶ not_found ──▶ «нет в каталоге — вот аналоги» + топ-10
```

- `search_api/verdict.py` — одна функция без состояния: проверка VLM топ-1,
  ответ «0» и вероятность выбора (без VLM — балл картинки и отрыв) →
  `match` / `not_found` и причина. Пороги — в `.env`.
- `search_api/sommelier.py` — правила по полям каталога (категория, крепость,
  температура, сорта, регион, блюда). Не зависит от FastAPI и Qdrant: каталог
  приходит списком payload, которые API на старте читает из Qdrant. Поэтому индекс остаётся единственным источником истины, а
  модуль проверяется на `catalog.jsonl` без сервиса (так же строятся демо-ответы
  `tools/web-demo/build_demo.py`).
- Поля сомелье (`dishes`, `temperature`, `description`, `public_rating`,
  `image_url`) лежат в payload. Обновить их без пересчёта векторов —
  `python -m indexer --payload-only`.
- Веб-интерфейс — статика без сборки, отдаётся тем же процессом: один порт,
  нет CORS. Фото сжимается в браузере до 1600 px по длинной стороне: серверу
  больше не нужно, а декодирование полного кадра было самым долгим шагом.

Модели загружаются на старте приложения (`lifespan`), а не по первому запросу:
на ответ отводятся секунды, загрузка весов в них не укладывается. Там же —
холостой поиск по белой картинке: первый проход через CUDA-ядра и первый запрос
к Qdrant в разы медленнее, без прогрева первый ответ занимал 3,4 с.

Настройки — переменные `WINE_*`; сервис и индексатор при запуске читают `.env`
из корня (уже заданные переменные окружения он не перекрывает).

## Хранилище

Qdrant, коллекция `wines`, косинусная метрика, размерность задаётся моделью
(1152 у `siglip2-so400m-patch16-512`). ID точки — детерминированный `uuid5` от
slug, поэтому переиндексация перезаписывает точку, а не плодит дубликаты.
