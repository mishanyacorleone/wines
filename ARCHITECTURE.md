# Архитектура

Сервис распознаёт вино по фотографии этикетки и возвращает карточку из каталога
«Своё Вино». Задача решается как **retrieval**, а не классификация: каталог
пополняется примерно на 50 позиций в день, и переобучать модель под каждое новое
вино нельзя. Новое вино = один новый вектор в индексе.

## Границы слоёв

Каждый сервис отвечает за одно и живёт в своём контейнере. Модели — отдельно
от API, страница — отдельно от API: упавший или перезапускающийся сервис
отключает только свою функцию, а не весь сайт.

```
                  ┌───────────────────────┐
 vino-svoe.ru ───▶│ catalog-scraper (init)│──▶ data/catalog/ ◀── catalog (синхронизация по кнопке
                  │  sitemap → NUXT → PNG │     images/*.png       и расписанию: новые вина →
                  └───────────────────────┘     catalog.jsonl      embedder → Qdrant → api)
                                                      │
                  ┌───────────────────────┐           │
                  │   indexer (init, GPU) │◀──────────┘
                  │ фото → вектор → upsert│
                  └───────────┬───────────┘
                              ▼
                        ┌──────────┐
                        │  Qdrant  │  2097 точек, dim 1152, cosine
                        └──────────┘
```

Во время работы наружу смотрит один порт — шлюз:

```
 браузер, скрипт оценки
          │ :8080
   ┌──────▼──────┐  /app/, /catalog-images/  ┌─────────┐
   │   gateway   │──────────────────────────▶│   web   │ nginx: страница сканера, фото бутылок
   │   (nginx)   │                           └─────────┘
   │ только      │  /v1/auth, /v1/me, /v1/map, /v1/admin… ┌─────────┐   ┌──────────┐
   │ маршруты    │───────────────────────────────────────▶│  users  │──▶│ Postgres │◀─┐
   │             │  /v1/events, /v1/admin/analytics       ┌─────────┐   └──────────┘  │
   │             │───────────────────────────────────────▶│analytics│─────────────────┘
   │             │  /v1/admin/catalog                     ┌─────────┐
   │             │───────────────────────────────────────▶│ catalog │──▶ сайт, embedder, Qdrant, api
   │             │  /v1/eval/predict, /v1/scan, /v1/…     ┌─────────┐   ┌──────────────────────┐
   └─────────────┘───────────────────────────────────────▶│   api   │──▶│ embedder (GPU)       │ SigLIP 2: фото → вектор
                                                          │ без GPU │   ├──────────────────────┤
                                                          │         │──▶│ vllm (GPU)           │ Qwen3-VL-4B-FP8: выбор + проверка
                                                          │         │   ├──────────────────────┤
                                                          └─────────┘──▶│ Qdrant               │ кандидаты + карточки
                                                                        └──────────────────────┘
 logs ── Docker API ──▶ logs/<дата>/all.log, logs/<дата>/services/<сервис>.log
```

| Компонент | Ответственность | Чего НЕ делает |
|---|---|---|
| `infra/gateway` | nginx: один порт :8080, маршрутизация по префиксу пути; за упавший сервис — JSON 503 с понятным текстом; номер запроса `X-Request-ID` | без логики и без статики |
| `services/web` | nginx: страница сканера `/app/` (`services/web/app`) и фото бутылок `/catalog-images/` | не ходит в API — это делает браузер |
| `services/search-api` (api) | HTTP-контракт, порядок шагов распознавания, решение «нет в каталоге», каталог в памяти, сомелье, карточки | без моделей и GPU; не строит индекс, не знает о пользователях |
| `services/embedder` | только модель SigLIP 2: фото → вектор (`POST /v1/embed`) | не знает про Qdrant и каталог |
| `vllm` (образ `vllm/vllm-openai`) | только инференс VLM: вероятности меток по OpenAI API | не знает про каталог, промпты и пороги — их держит api |
| `services/catalog-service` (catalog) | синхронизация с сайтом: новые вина → фото → вектор (embedder) → Qdrant → api перечитывает каталог; расписание и история | не распознаёт; код парсера и записи в индекс — общий с catalog-scraper и indexer |
| `services/user-service` | аккаунт, профиль, история сканов, оценки, достижения и их правила (PostgreSQL) | не распознаёт, не ходит в api; каталог читает из Qdrant |
| `services/analytics-service` | события веб-сканера (`/v1/events`) и отчёт для дашборда РСХБ; демо-данные | не хранит пользователей: кто админ — спрашивает `users`, пересылая cookie |
| `services/log-collector` (logs) | читает stdout всех контейнеров проекта и раскладывает по дням и сервисам | сервисы о нём не знают — пишут в stdout |
| `libs/wine-embeddings` | модель, нормализация фото, лимит VRAM, кэш весов (embedder и indexer) | ничего не знает про Qdrant и HTTP |
| `libs/wine-logging` | единый формат логов Python-сервисов, номер запроса, строка о проблемном запросе | — |
| `services/catalog-scraper`, `services/indexer` | первый сбор каталога и полный индекс (`infra/init.sh`, профиль init) | не работают постоянно |
| `tools/eval-runner` | прогон выборки, метрики точности и времени, нагрузка (RPS), отчёт | не лезет в Qdrant напрямую, работает только через API |

## Отказоустойчивость: что видит пользователь

| Упал или перезапускается | Что происходит |
|---|---|
| embedder или Qdrant | сканер: «Распознавание временно недоступно — попробуйте через минуту» (503); страница, кабинет, карта, карточки вин из истории работают |
| vllm | сканер отвечает по одной картинке (`reason: vlm_unavailable`): «упрощённый режим — выберите своё вино из похожих», 10 вариантов; `/v1/eval/predict` отдаёт топ-1 по картинке |
| api | шлюз отвечает JSON 503 на сканер, карточки и подбор к блюду; страница, кабинет, достижения, карта (без справки по региону) работают |
| users, analytics, catalog | недоступен только свой раздел; сканер работает |
| web | страница не открывается (шлюз пишет «сайт перезапускается»); API, включая контракт организатора, работает |

Как это сделано:
- **Сервисы не ждут друг друга при старте.** api поднимается за секунды, каталог
  читает из Qdrant в фоне с повторами; модели вызываются по запросу.
- **Быстрый отказ.** Таймаут соединения к моделям — 2 с; после сбоя сервис
  помечается недоступным на 10 с (`search_api.remote.Breaker`), запросы в это время
  сразу получают отказ, а не ждут таймаута. Переходы «упал / поднялся» — одной
  строкой в логе.
- **Шлюз не зависит от сервисов.** Адреса спрашивает у DNS Docker на каждый запрос,
  у упавшего сервиса — `error_page` с JSON; своя проверка здоровья `/gateway-health`.
- **`/health` api** — 200, пока жив процесс, а состояние зависимостей — в
  `components` (`status: degraded`): упавшая модель не повод перезапускать api.

## Ключевое архитектурное решение: общий энкодер

`libs/wine-embeddings` вынесен в отдельную библиотеку, которую используют и
индексатор, и API. Это не борьба с дублированием кода, а корректность: если
индекс построен одним препроцессингом, а запрос кодируется другим, векторы
окажутся в разных частях пространства. Поиск при этом продолжит «работать» —
просто станет возвращать мусор, и ни логи, ни тесты этого не покажут.

## Поток обработки запроса

Порядок шагов — в api (`search_api.search`), асинхронно: пока один запрос ждёт
модель, api принимает следующие, и vLLM собирает параллельные запросы в батч.

1. **Нормализация** (`wine_embeddings.preprocessing`) — EXIF-поворот, альфа-канал
   на белый фон, паддинг до квадрата без растяжения. Каталожные PNG вертикальные
   (медиана 340×1080), фото с телефона — 3024×4032; прямой resize деформировал бы
   бутылку в этих случаях по-разному.
2. **Эмбеддинг** (сервис embedder, `wine_embeddings.encoder`) — SigLIP 2, только vision-башня;
   текстовая не загружается, поиск идёт картинка-к-картинке. Вектор L2-нормализуется,
   поэтому скалярное произведение в Qdrant и есть косинус.
3. **Поиск** — Qdrant, косинусная метрика, топ-k с payload (slug, url, метаданные).
   Payload самодостаточен: после поиска второго похода в базу нет.
4. **Выбор VLM** (`search_api.vlm`, модель — в сервисе vllm; `WINE_VLM_ENABLED=0` —
   выключить; промпты, картинки и пороги держит api, vLLM отдаёт только вероятности меток) —
   Qwen3-VL-4B получает фото пользователя и первые 5 из топ-10 (текст карточки +
   уменьшенное эталонное фото, кэш `data/catalog/vlm-refs-*`) и за один прямой
   проход без генерации отдаёт вероятности ответов «1»…«5» и «0» (ни одна не
   подходит). Пятёрка пересортировывается по ним, места 6–10 идут следом в
   порядке векторного поиска — это рекомендации для интерфейса. Картинка надёжно находит
   линейку (top-5 = 100%), VLM выбирает внутри неё — различает цвет, сладость и
   стилизованные надписи.
5. **Проверка топ-1** (`verify`) — второй проход, ~150 мс: фото +
   эталон выбранного вина, «одно и то же вино?» (этикетка, текст на бутылке,
   форма бутылки, цвет вина) → вероятность «Да». Выбирая
   из многих, VLM почти всегда называет самое похожее вино; попарный вопрос
   отличает «другое вино того же производителя» — на нём держится «нет в каталоге».
   OCR (EasyOCR) был здесь до 28.09.2026 и убран: с VLM он не добавлял точности.
6. **Ранжирование** (`search_api.search`) — без VLM softmax с температурой 0.05 переводит
   баллы в `confidence`, с VLM `confidence` — его вероятность. Без температуры распределение было бы почти равномерным:
   соседние кандидаты различаются в сотых долях. Отдельно считается `margin` —
   отрыв первого от второго, прямое требование ТЗ.

## Контракты API

| Метод | Назначение |
|---|---|
| `POST /v1/search` | `top1` (slug для метрики) + топ-k (по умолчанию 10): slug, ссылка, метаданные, confidence, разбивка времени + решение `status`/`reason`/`message`, `verify_prob` |
| `POST /v1/eval/predict` | контракт скрипта кейсодержателя: плоский `{"slug": "..."}` |
| `POST /v1/scan` | ручка мобильного сканера: решение + карточка с советами сомелье или «нет в каталоге — вот аналоги» + топ-10 |
| `GET /v1/wines/{slug}`, `GET /v1/pairing`, `GET /v1/pairing/dishes` | карточка по выбору пользователя, вина к блюду |
| `GET /v1/regions`, `GET /v1/regions/{регион}/wines` | винная карта: регионы каталога (вин, виноделен, главные сорта, фото) и что попробовать из региона |
| `POST /v1/feedback` | отклик «да / выбрал другое / моего нет» → `data/feedback/feedback.jsonl` |
| `GET /app/` | мобильный интерфейс — отдаёт сервис web (`services/web/app`) |
| `GET /health` | жив ли api и состояние зависимостей: Qdrant, каталог в памяти, embedder, vLLM (`status`: ok / degraded) |
| `POST /internal/catalog/reload` | перечитать каталог из Qdrant (зовёт catalog после добавления вин); шлюз снаружи не пускает |

Сервис каталога (`services/catalog-service`, только админ):

| Метод | Назначение |
|---|---|
| `GET /v1/admin/catalog/sync` | идёт ли синхронизация (и её шаг), вин в поиске, расписание, следующий запуск, история |
| `POST /v1/admin/catalog/sync` | запустить сейчас (202; 409 — уже идёт) |
| `PUT /v1/admin/catalog/sync/settings` | расписание: `auto`, `times`, `per` (`minute` / `hour` / `day` / `week` / `month`) — «N раз в период», не чаще раза в минуту |

Сервис пользователей (`services/user-service`, за тем же шлюзом):

| Метод | Назначение |
|---|---|
| `POST /v1/auth/register`, `/login`, `/logout` | вход по почте или телефону и паролю; сессия — HttpOnly-cookie `wine_session` |
| `GET/PATCH/DELETE /v1/me`, `PUT /v1/me/avatar` | профиль, статистика, достижения с прогрессом; имя и аватар; удаление аккаунта |
| `GET/POST /v1/me/scans`, `PATCH/DELETE /v1/me/scans/{id}` | история сканов: запись после `/v1/scan`, правка в «Не то вино?»; в ответе `new_region` — регион, впервые открытый этим сканом |
| `GET /v1/me/regions` | винная карта пользователя: открытые регионы (с учётом сопоставлений админа), попробованные в них вина, дата открытия |
| `GET /v1/map/zones` | регионы карты (какие субъекты РФ занимают) и сопоставления админа |
| `GET /v1/settings/share`, `PUT /v1/admin/settings/share` | шаблон текста «Поделиться вином» с масками; правит админ |
| `/v1/admin/map/zones[/{id}]`, `/v1/admin/map/aliases` | админ: создать, изменить, удалить регион карты; отнести регион каталога к региону карты |
| `PUT /v1/me/ratings/{slug}` | нравится / не нравится — только для вин из своей истории |
| `GET /v1/achievements`, `GET /v1/avatars` | все достижения (у вошедшего — с отметкой и прогрессом), готовые аватары |
| `/v1/admin/achievements[/rules]` | админ: список, правила, создание, правка, удаление достижений |
| `GET /v1/media/{avatars,scans,achievements}/{file}` | загруженные картинки |
| `GET/POST /v1/me/diary`, `PUT/DELETE /v1/me/diary/{id}` | дневник дегустации: «попробовал» (оценка 1–5, чипы вкуса, заметка, «где, с кем, с чем») и «хочу попробовать» |
| `GET /v1/quiz/today`, `POST /v1/quiz/today/answer` | вопрос дня (без аккаунта — ответить можно, серия не копится); `/v1/admin/quiz[/{id}]` — свои вопросы админа |
| `GET /v1/challenges`, `GET /v1/me/prizes` | идущие челленджи с прогрессом; выданные промокоды; `/v1/admin/challenges`, `/v1/admin/prizes` — редактор |
| `POST /v1/gifts`, `GET /v1/gifts/{id}`, `POST /v1/gifts/{id}/save` | подарочная открытка: создать (можно без аккаунта), открыть по ссылке, сохранить себе (с аккаунтом) |
| `GET /v1/me/year`, `GET /v1/settings/year`, `PUT /v1/admin/settings/year` | «Мой винный год»: итоги; включает админ, сам админ видит всегда |

## После поиска: решение и сомелье

```
выдача топ-10 ──▶ verdict.decide ──▶ match ──▶ карточка топ-1 + sommelier.advise + sommelier.similar
                                   └─▶ not_found ──▶ «нет в каталоге — вот аналоги» + топ-10
```

- `search_api/verdict.py` — одна функция без состояния: проверка VLM топ-1,
  ответ «0» и вероятность выбора (без VLM — балл картинки и отрыв) →
  `match` / `not_found` и причина. Пороги — в `.env`.
- `search_api/sommelier.py` — правила по полям каталога (категория, крепость,
  температура, сорта, регион, блюда). Не зависит от FastAPI и Qdrant: каталог
  приходит списком payload, которые API на старте читает из Qdrant. Поэтому индекс остаётся единственным источником истины, а
  модуль проверяется на `catalog.jsonl` без сервиса (так же строятся демо-ответы
  `tools/web-demo/build_demo.py`).
- Поля сомелье (`dishes`, `temperature`, `description`, `public_rating`,
  `image_url`) лежат в payload. Обновить их без пересчёта векторов —
  `python -m indexer --payload-only`.
- Веб-интерфейс — статика без сборки в сервисе web; браузер ходит в API через тот
  же шлюз: один адрес, нет CORS. Фото сжимается в браузере до 1600 px по длинной
  стороне: серверу больше не нужно, а декодирование полного кадра было самым долгим шагом.

Модели загружаются на старте своих сервисов (embedder, vllm), а не по первому
запросу: на ответ отводятся секунды, загрузка весов в них не укладывается. embedder
на старте делает холостой проход по белой картинке: первый проход через CUDA-ядра
в разы медленнее, без прогрева первый ответ занимал 3,4 с.

Настройки — переменные `WINE_*`; сервис и индексатор при запуске читают `.env`
из корня (уже заданные переменные окружения он не перекрывает).

## Личный кабинет

Сканировать можно без аккаунта: сервис распознавания о пользователях ничего не
знает. Страница сначала получает ответ `/v1/scan`, затем — если человек вошёл —
записывает скан в `users` (slug + превью фото 480 px). Без аккаунта сканы копятся
в браузере (до 20) и переносятся в историю при входе; под результатом —
ненавязчивое предложение войти, его можно закрыть до конца сессии.

- **Снимок карточки в скане.** `users` берёт регион, сорта и категорию вина из
  Qdrant (та же коллекция, только чтение) и сохраняет снимок в строке скана: история
  и достижения не зависят от того, жив ли search-api и не сняли ли вино с сайта.
- **Достижения — данные, а не код.** Админ собирает условие из готовых правил
  (`user_service/achievements.py`, `RULES`): тип + порог (+ значение, например
  регион). Проверка — после скана, правки скана, оценки и при открытии профиля
  (так выдаются и достижения, добавленные позже). Выданное не отзывается.
- **Роли.** `user` и `admin`; админ создаётся при старте из `WINE_ADMIN_LOGIN` /
  `WINE_ADMIN_PASSWORD` (без пароля — генерируется и пишется в лог).
- **Безопасность.** Пароли — scrypt; в БД только хэш токена сессии; загруженные
  картинки перекодируются Pillow (EXIF и чужое содержимое не уходят наружу);
  10 неудачных входов за 5 минут с адреса → 429.
- **Фронтенд** — `services/web/app/account.js` поверх сканера: `app.js` отдаёт
  события `wine:scanned` / `wine:picked` и общие функции (`window.Wine`). Нет
  сервиса пользователей (упал или запуск без шлюза) — кабинет просто не показывается.
- Схема создаётся при старте (`create_all`); когда она начнёт меняться на живых
  данных — подключить Alembic.

## Винная карта России

Интерактивная карта всех субъектов РФ (приближение, перемещение, подписи по
масштабу); субъекты винных регионов выделены, открытые пользователем — закрашены.
Каталог регионов (число вин) — сервис распознавания (`/v1/regions`), какие
субъекты входят в регион карты — сервис пользователей (`/v1/map/zones`, таблицы
`wine_zones`, `zone_aliases`), прогресс — `/v1/me/regions`.

- **Как вино встаёт на карту.** Поле `region` вина сравнивается с названиями
  регионов карты (без учёта регистра, «ё», тире). Совпало — вино на карте. Нет
  («Краснодарский край», «Сибирь») — регион попадает админу в «Не сопоставлено»
  (`/app/#admin` → «Регионы карты»): отнести к существующему региону карты
  (сопоставление) или создать новый, отметив субъекты кликами по карте. На этом же
  сопоставлении считаются прогресс, «новый регион» и достижения за регионы.
  Стартовые 9 регионов карты засеваются на пустой базе (`user_service/zones.py`).
- **Контуры** — `services/web/app/russia-map.json` (85 субъектов, 117 КБ, общий
  вид) и `russia-map-detail.json` (367 КБ, подгружается при приближении ×2),
  собирает `tools/region-map/build_map.py` из Natural Earth admin-1 (общественное
  достояние): коническая Альберса (100° в. д.), официальные названия субъектов,
  точка подписи внутри контура. Шлюз сжимает их gzip.
- **Удержание:** скан вина из нового региона — поздравление «Новый регион на
  карте» (до достижений), на карте — «следующий шаг» (регион с наибольшим числом
  вин, ещё не открытый), в шторке региона — что из него попробовать. Достижения
  за регионы — обычные правила `regions` и `region`.
- Фронтенд — `services/web/app/map.js` без внешних библиотек: `MapView` (колесо,
  щипок, перетаскивание в границах страны, кнопки, подсказка), экран `#map`,
  мини-карты, поздравление, админка регионов; `account.js` берёт их через
  `window.WineMap`. Бэкап первой версии (юг + Россия, 9 регионов в коде) —
  `backups/wine-map-v1-2026-10-18/` (локально, не в git).

## Поделиться

`services/web/app/share.js`: картинка 1080×1350 рисуется в браузере (canvas) —
вино (бутылка, факты, блюда), достижение (значок, имя) или винная карта (открытые
регионы). На картинке QR-код (`web/vendor/qrcode.js`, qrcode-generator, MIT) —
страница вина на vino-svoe.ru, иначе главная сайта. Кнопки: Telegram и
ВКонтакте (по ссылке они принимают только адрес и текст — уходит ссылка на
vino-svoe.ru, а не на стенд) и «Сохранить» — картинку прикрепляют вручную.
У ВК нет параметра для поля «Ваше сообщение»: `title` — заголовок карточки ссылки
(туда идёт название вина), а текст по шаблону копируется в буфер с подсказкой
«вставьте Ctrl+V»; на http-адресе стенда — запасным способом (`execCommand`).
Системное меню «Отправить…» (`navigator.share` с файлом и текстом; ссылка — внутри
текста, не в поле `url`, иначе часть приложений берёт только ссылку) показывается,
только если браузер умеет делиться файлом (`navigator.canShare`), а это лишь на
https или localhost: на `http://<IP>:8080` кнопки нет (поэтому 18.10 оно «не доходило»),
проверено на iPhone по https. Как в приложениях, меню открывается сразу по «Поделиться»,
если браузер ещё считает действие нажатием (`navigator.userActivation.isActive`);
если картинка рисовалась дольше — остаётся кнопка. Фото с чужого домена грузится с
`crossOrigin`: без CORS оно не рисуется, но и не блокирует сохранение картинки.
Текст «Поделиться вином» — шаблон в таблице `settings` сервиса пользователей,
правит админ (`/app/#admin` → «Поделиться»): маски `{название}` `{сорт}` `{сахар}`
`{цвет}` `{бренд}` `{регион}` `{ссылка}` подставляет `share.js` (сахар и цвет — из
категории вина); пустая маска убирается вместе с лишней запятой. Бэкап версии без
шаблона — `backups/share-v1-2026-10-18/`.

## Аналитика для РСХБ

Отдельный сервис `analytics` (FastAPI, таблица `analytics_events` в том же
PostgreSQL). Страница шлёт события: просмотр, скан (найдено / нет в каталоге,
вино, регион, время ответа), «поделиться» (что и куда), карта и регион,
предложение войти и клик по нему, регистрация, вход, достижение. Модули страницы
сообщают о действии событием `wine:track`, отправляет `web/analytics.js`.
Посетитель — случайный id в браузере; адрес клиента подставляет шлюз (X-Real-IP).
Контракт организатора в аналитику не попадает: события шлёт только веб-сканер.

Дашборд (`/app/#admin` → «Аналитика», только админ — `analytics` проверяет cookie
через `users`): сканы, посетители и вернувшиеся, конверсия «скан без входа →
регистрация», доля «нет в каталоге» (спрос на вина вне каталога — лиды на новых
производителей), шары, сканы по дням, воронка регистрации, топ вин, регионов и
виноделен, винная карта, сети провайдеров (адрес без последнего октета). Отчёт
считается в Python по событиям периода — на пилоте агрегаты переезжают в SQL или
ClickHouse без смены формата. Город по адресу — подключением локальной базы GeoIP.

На демо все запросы идут с одного адреса — кнопка «Сгенерировать демо-данные»
(вина из настоящего каталога, рост аудитории, выходные, возвраты): события
помечены `demo`, дашборд пишет об этом, «С демо-данными» снимается одной галочкой,
«Удалить демо» — одной кнопкой; настоящие события не трогаются.

| Метод | Назначение |
|---|---|
| `POST /v1/events` | событие со страницы (тип, id посетителя, параметры); 120 в минуту с адреса |
| `GET /v1/admin/analytics?days=&demo=` | отчёт за период |
| `GET /v1/admin/analytics` → `engagement` | вовлечение: вопрос дня, дневник, открытки, призы, итоги года; `registration_sources` — какой призыв войти (`auth_prompt` с `source`, `nudge_click`) был последним перед регистрацией и его конверсия |
| `GET/PUT /v1/me/taste`, `GET /v1/me/taste/match?slug=` (users) | «Мой вкус» и «понравится ли это вино»: профиль (цвет, сладость, сорта, винодельни) + оценки похожих вин (★ дневника, 👍/👎) → процент, вердикт, причины, «вы уже пили» |
| `GET /v1/taste/options` (api) | сорта каталога по числу вин с фото сайта и винодельни — для экрана «Мой вкус» |
| `GET /v1/wineries`, `GET /v1/wineries/{slug}` (api) | «От бутылки — на винодельню»: метки виноделен для карты (точка, туры, вин в каталоге); страница — о винодельне, терруар, люди, туры, вина каталога, соседи, туры региона. Снимок сайта — `search_api/wineries.json` (`tools/site-media/fetch_wineries.py`); у карточки вина — поле `winery` (связь по `manufacturer_slug`) |
| `GET /v1/me/trips`, `PUT/DELETE /v1/me/trips/{winery}` (users) | «Хочу съездить»: список виноделен человека (только с аккаунтом) |
| `GET /v1/admin/analytics` → `feedback` | точность распознавания по ответам «Это ваше вино?» (`recognition`: confirmed / picked_alternative / none_match) по неделям; ★ дневника и 👍/👎 истории (`rate`); в Excel — листы «Точность распознавания» и «Оценки» |
| `GET /v1/admin/analytics/export.xlsx?days=&demo=` | тот же отчёт в Excel: сводка, по дням (с графиком), воронка, топы, шары, сети, события периода (до 50 000) |
| `POST/DELETE /v1/admin/analytics/demo` | сгенерировать / удалить демо-данные |

## Вовлечение: дневник, вопрос дня, челленджи, призы, открытки, итоги года

Всё в сервисе пользователей (`diary.py`, `quiz.py`, `rewards.py`, `gifts.py` рядом с `main.py`): это данные
пользователя, а прогресс челленджей считается по его сканам, записям и ответам — отдельного сервиса
и межсервисных вызовов не нужно. Страница — `web/app/engage.js` (главная, карточка, профиль) и
`engage-admin.js` (Управление → «Задания и призы»).

- **Принцип регистрации:** что пользователь копит (записи, серия, призы), хранится только с аккаунтом.
  Без него можно ответить на вопрос и заполнить запись — на «Сохранить» страница предлагает войти и
  после входа сохраняет сама (ответ на вопрос дня засчитывается в серию).
- **Вопрос дня:** вопрос админа на свою дату (дата обязательна), иначе — «Угадайте вино»: вопрос по бутылке из
  каталога (регион / сорт / цвет / сладость, детерминирован датой — у всех один). Очереди «без даты» нет (убрана
  20.10). Поставить свой вопрос на день, на который уже отвечали, нельзя. Серия — дни с ответом подряд; день — по Москве
  (`WINE_USERS_UTC_OFFSET_HOURS`, 3).
- **Призы:** список кодов (каждому свой) или один общий; выдаются за серию N дней, за достижение или за
  челлендж — один раз за одно и то же (`promo_issues`, уникально по пользователю и источнику). Коды
  кончились — приз не выдаётся, предупреждение в логе. Скидку даёт партнёр — сервис только раздаёт коды.
- **Челлендж:** даты, что сделать (вина / записи / ответы), сколько, фильтр вин (регион, сорт, категория,
  винодельня), приз. Проверка — лениво: после скана, записи, ответа и при открытии профиля.
- **Достижения:** новые правила — «записей в дневнике», «дней подряд в вопросе дня».

## Хранилище

Qdrant, коллекция `wines`, косинусная метрика, размерность задаётся моделью
(1152 у `siglip2-so400m-patch16-512`). ID точки — детерминированный `uuid5` от
slug, поэтому переиндексация перезаписывает точку, а не плодит дубликаты.

## Каталог: новые вина без перезапуска

По ТЗ в каталог добавляется до ~50 вин в день. Новое вино — одна точка в Qdrant,
переобучать ничего не нужно. Сервис `catalog` (`catalog_service.sync`):

1. парсер (тот же `catalog_scraper`) берёт свежий sitemap vino-svoe.ru и скачивает
   только вина, которых ещё нет в `data/catalog` (фото + карточка);
2. вина каталога, которых нет в Qdrant, получают вектор от embedder и записываются
   в индекс с тем же payload и id точки, что у индексатора (`indexer.catalog`,
   `indexer.store`) — переиндексация потом ничего не задвоит;
3. api перечитывает каталог в память (`/internal/catalog/reload`; плюс сам
   сверяет число точек с Qdrant раз в минуту) — вино сразу в поиске, карточках,
   подборе к блюду и на карте; `users` видит новые регионы в течение 10 минут.

Запуск — кнопкой в админке (`/app/#admin` → «Каталог») или по расписанию: раз в N
часов от конца прошлого запуска, интервал и вкл./выкл. — там же (хранится в
`data/catalog/sync-state.json` вместе с историей запусков). Вина, снятые с сайта,
из поиска не удаляются — отчёт их только считает.

Если выход в интернет только через прокси на 127.0.0.1 хоста (машина разработки),
контейнер до него не дотянется: ретранслятор `egress` (профиль `proxy`,
`infra/egress/relay.py`) слушает адрес docker0 и передаёт байты прокси как есть.

## Логи

Сервисы пишут в stdout, как принято в контейнерах; сборщик `logs` читает stdout
всех контейнеров проекта через Docker API и раскладывает по дням:

```
logs/2026-10-19/
├── all.log               важное по всем сервисам: события, ошибки, медленные запросы, Docker
└── services/
    ├── api.log           всё по одному сервису
    ├── gateway.log       журнал доступа шлюза — каждый запрос к API
    └── …
```

Строка — одно событие: `2026-10-19 14:58:42.039 INFO  api  scan  [33319c71] Скан: найдено
«Розовое полусладкое» — выбор VLM 0.99, проверка 0.35 · 1,42 с (вектор 35 мс · Qdrant 20 мс ·
VLM 341 мс)`. Принципы:

- **События, а не трафик.** В логе — что произошло: скан и его итог, вход, регистрация,
  достижение, правка админа, синхронизация каталога, сервис упал / поднялся. Каждый HTTP-запрос
  в лог сервиса не пишется — только ошибки (4xx/5xx) и медленные; полный журнал
  запросов — у шлюза в `services/gateway.log`.
- **Одна проблема — одна строка в all.log.** Скан сам пишет итог, время и «— медленно» (дольше
  SLA 3 с — WARN) или «X недоступен → 503» и помечает запрос (`wine_logging.mark_logged`) —
  строки «→ 503 за …» от middleware и от шлюза для него в all.log уже не нужны. От шлюза в all.log
  попадают только запросы, не дошедшие до сервиса (`/internal/`, сервис лежит — рядом строка nginx
  «сервис за шлюзом не отвечает»). Известные предупреждения vLLM на старте (нет FP8-ядер у
  RTX 3090, параметры выборки из generation_config) — только в `services/vllm.log`.
- **Шум отсеивается сборщиком:** журнал доступа Qdrant и vLLM, проверки здоровья,
  плановые контрольные точки Postgres, полосы загрузки весов — либо только в
  `services/<сервис>.log`, либо не пишутся вовсе.
- **Номер запроса** (`[33319c71]`) задаёт шлюз (`X-Request-ID`) и передаёт по цепочке:
  api → embedder → vLLM, catalog → users. По нему в all.log виден путь одного скана.
- **События Docker** — тоже в all.log: «контейнер api остановился: убит (код 137)»,
  «vllm готов», «проверка здоровья не проходит».
- Персональные данные маскируются (`m***@gmail.com`); логи старше 30 дней удаляются.
